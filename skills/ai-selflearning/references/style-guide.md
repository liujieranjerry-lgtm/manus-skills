# Style Guide：结构、术语、代码与语言

这是“通用知识版”文章的风格与结构规则。目标读者：没有代码基础、但很聪明，想深入掌握知识的人。文章要像一位编辑认真写出的长篇讲义，而不是聊天回复或百科词条。

## 结构骨架（递进式）

1. **开场立靶**：用一个具体场景或一个“大多数人跳过的问题”开场，让读者第一段就知道这篇文章要补什么。不要用“本文将介绍……”这类空话开场。
2. **地基到楼顶**：先讲清最基础的概念，再逐层叠加边界、分类、原理、判断标准。每一层都要让读者看见它和上一层的关系，禁止并列堆砌知识点。
3. **企业级密度**：核心概念必须覆盖：定义、分类/边界、判断标准、容易混淆的术语陷阱、真实产品或案例。密度宁多勿少，篇幅不设上限；删减的优先级永远是“已知内容”而不是“新知识”。
4. **常见误解板块**：正文收尾前写“常见误解”，用“误解一/二/三”的格式：先点破一个反直觉的常见说法，再给出准确辨析，并把每个误解和文章前文或源材料的观点挂钩。误解要有代表性，不能凑数。
5. **收束**：用可带走的分层结论或一组检查问题收尾，让读者读完能自己判断和复用。

## 术语处理

- 所有技术名词在第一次出现时解释，解释有机融入正文，不单独放术语表。
- 解释要克制：一句话讲清本质，必要时用一个生活化类比；一个段落最多一个类比。
- 如果某个基础术语不讲清就会挡住后面的内容，优先完整讲清它，再继续串联，不要为了避免打断行文而跳过。
- 产出后把自己当作没有代码基础的读者通读一遍，找出任何可能不懂却没有解释的名词，逐一补齐；补齐不得破坏行文规范和逻辑。

## 代码处理（参考 code-explainer 的叙事方法）

- 不到万不得已不引入代码；必须用代码表达核心逻辑时，只保留最小片段：接口、伪代码、结构化输出、最小执行片段。大段组合代码删除。
- 每个代码块用“一段式叙事”解释：角色句（这段代码在整个系统里负责什么）→ 按真实执行顺序走一遍 → 价值句（它保证了什么、为什么重要）。整体是一段连贯叙述，不要拆成逐行注释表。
- 保留代码里的原名并用反引号标出，不用“那个方法”“这个字段”代替；把标识符翻译成现实角色（合同、登记簿、承诺、事件流等）。
- 只解释代码里实际出现的语法，不假设读者懂任何编程语言；多个代码片段当作同一个系统串联解释。

## 语言

- 干练、有逻辑、递进式；不用“简单说就是”“本质上只是”这类降密度的说法，不答琐碎内容。
- 不使用职业视角（“对工程师而言”“作为开发者”），不用居高临下的语气。
- 连贯和知识递增优先于篇幅；允许长文，但不允许注水。

## 自检清单

交付前逐项检查：

- [ ] 开场立靶是否明确，读者知道这篇补什么？
- [ ] 文章是否只依据给定材料写作，没有假设读者已学过某些内容？
- [ ] 每个技术名词是否都在首次出现处解释过？有没有割裂的术语表？
- [ ] 代码块是否按“角色 → 执行顺序 → 价值”解释，且保留了全部原标识符？
- [ ] 是否有“误解 → 辨析 → 挂钩前文/材料观点”的板块？
- [ ] 结尾是否有可带走的结论或检查问题？
- [ ] 不依赖原文，文章本身能否独立读懂？
- [ ] 是否忠实材料，增补的解释与材料原意可区分？
- [ ] 具体断言是否已按 fact-discipline 处理干净？
